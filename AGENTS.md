# Repository agent instructions

This repository supports one organizer and up to seven Codex, Claude Code, or Devin coding workers. Read the governing protocol in `docs/ROADMAP.md` section 1.5. For the fixed eight-session local desktop workflow, also follow the executable role recipe in `docs/DESKTOP-SESSIONS.md` and the checkout's ignored `SESSION.md`.

- Before changing code, read the current task packet and a bounded roadmap path: `docs/ROADMAP.md` section 1.1 (boundaries), 1.5 (protocol), the section 11 status tables, and the newest three dated entries at the end of section 17 (the dated progress log, newest last). Open other sections only when the packet cites them. The roadmap is the single source of truth; do not create a competing plan or continuation file.
- Which checkout is authoritative: current code is `origin/main`. `Quant Office\repo` is only the Git anchor that owns the worktrees; its own checkout is stale, so never implement or review there, and never move or rename it. Batch work happens in `repo-sessions\<batch>\*`. Ad-hoc work outside a batch uses a new worktree and branch under `Quant Office\Worktrees\`, created from `origin/main`.
- Record `git status --short --branch`, the current commit, branch, and worktree before editing. Treat stale roadmap hashes as navigation hints, not proof.
- Use one writer per checkout. Each batch freezes a reviewed base from `origin/main`; every worker gets its own worktree (or isolated hosted clone) and branch from that exact commit. Never run two writing sessions in the same directory. A reviewed feature commit may be used for a setup pilot before its PR merges, but report that base explicitly.
- Keep each branch scoped to one task packet and avoid overlapping file ownership across active sessions. Commit only that session's changes. Do not force-push, rewrite shared history, delete another session's branch/worktree, or push directly to `main`. In another session's checkout, do not run `git clean`, `git worktree remove/prune` or `git stash` either. The stash stack is shared by every worktree, and untracked files there may be safety copies.
- Preserve the execution and safety boundaries in roadmap section 1.1. Local tests do not establish hosted-provider, scientific, brokerage, or live-research capability.
- Workers follow the organizer's objective, file ownership and acceptance packet. Shared types, IPC bridges, store schemas, dependencies, CI, agent rules and the roadmap are organizer-owned. Report required cross-scope changes instead of silently editing them.
- Workers return a proposed roadmap entry with changed files, commands, results and blockers in their PR. Only the organizer writes the canonical roadmap after integration. Do not claim tests or provider operations that did not run.
- On integration the organizer appends the dated entry to section 17 **and** updates the matching section 11 row. Date entries with the local date of the recorded commit (`git log -1 --date=short-local`), not UTC.
- Run application commands from `app`. If `node` is not on `PATH`, use `C:\Program Files\nodejs\node.exe` as recorded in the roadmap. Do not run live-provider fixtures unless the current task explicitly authorizes them.
- After every integrated revision touching `app/`, Session 8 rebuilds `app/dist`, repackages `app/release` (`node scripts/build.mjs && node scripts/package.mjs` from `app/`), and mirrors the output into the user-facing install at `Quant Office\App\` (sibling of `repo-sessions\` — the taskbar pin's target) before declaring the round done. Both packaged copies must match the round's accepted HEAD; verify the app is closed before overwriting `App\`, and record the SHA-256 of `App\resources\app.asar` in the roadmap entry.
- Worker PRs target the batch organizer branch. The organizer filters proposals, reviews exact commit SHAs, checks ownership, integrates one at a time and tests the combined result. Finish with branch/commit, checks, blockers and likely merge conflicts. Session 8 may merge its integration PR into `main` only after every worker is resolved, the round is closed, `origin/main` is an ancestor of the exact PR head, the required `verify` check succeeds for that same head, and required conversations are resolved. Direct pushes to `main` remain prohibited. Worker agents never merge into `main`. If Session 8 cannot inspect or perform the protected PR merge through an authenticated GitHub route, it reports the PR URL and blocker; it never requests or exposes a raw token and never substitutes a direct push.
- In a configured desktop batch, do not infer work from chat or the roadmap. Session 8 publishes with `node tools/desktop.mjs publish`; Sessions 1–7 act only on the packet returned by `node tools/desktop.mjs start`, then submit with `finish` or `block`. Only Session 8 accepts, rejects, updates the roadmap and closes the round.

## User data and acceptance testing

- The user's live office data is `%APPDATA%\Quant Research Office`. Never modify, reset or migrate it without an explicit request from the user in chat. Every backup goes to an absolute, dated path **outside any Git checkout** (for example `Quant Office\Archive\`), and the reply reports that path. Never write a backup to a path relative to the working directory.
- Tests, demos and acceptance runs use `QRO_USER_DATA_DIR` pointing at a scratch folder, never the live workspace.
- Any round that touches `app/src/renderer` needs a user-level check before it closes: open the packaged app with an isolated `QRO_USER_DATA_DIR` and exercise the changed UI as a user would. Unit tests and CI do not replace this. The standard test roster is Director = Claude Opus 5.5 (effort low, local), PM = Claude Sonnet 5 (effort low, local), Worker = Devin `swe-2-max` (local).
- When a provider releases or retires a model, the organizer updates `PROVIDER_MODEL_SUGGESTIONS` in `app/src/shared/effort.ts` and its review date in the same round.
