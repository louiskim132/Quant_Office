# ui-benchmark-1 — worker-2: VS Code comparator study

Comparator: **Visual Studio Code** (code.visualstudio.com product pages, `code.visualstudio.com/docs`, `code.visualstudio.com/api/ux-guidelines`, github.com/microsoft/vscode). Focus per packet: information density (explorer, panels, tabs), settings UX (Settings editor vs settings.json, search), navigation model (command palette, quick open, breadcrumbs, sidebar).

Baseline: packaged `App\` build mirroring `main@65bddec`, captured by the organizer at `drafts/organizer/ui-baseline/` (`empty/` 13 shots, `populated/` 13 shots, `live/` 12 shots).

## 1. Scope and capture method used per artifact

All artifacts were captured with source method **(a)** — direct free capture via Playwright (`app/node_modules/playwright`, headless Chromium 153, viewport 1600x1000) against public pages. No purchases, no gated content, no MCP reports needed — VS Code docs are capture-friendly and embed real product-UI screenshots. The capture driver is `swipe/worker-2/capture.mjs`; per-target results, page titles and embedded-image alt texts are recorded in `swipe/worker-2/capture-manifest.json`. Captured 2026-09-30.

Two artifact kinds per page:

- **Full-page screenshot** (`a-<name>.png`) — the doc/product page as rendered, including the docs site's own navigation.
- **Element screenshot** (`a-<name>-imgN.png`) — a direct capture of an embedded `<img>` (naturalWidth >= 480), i.e. a real VS Code product-UI image lifted from the page; alt text is preserved in the manifest.

Method (a) was sufficient everywhere; methods (b–d) were not needed. Limitation: these are doc/UX-guideline images chosen by Microsoft, not a live VS Code session under our control — see section 6.

## 3. Comparator scorecard — VS Code (1–5, evidence-cited)

| Dimension | Score | Evidence |
| --- | --- | --- |
| Information density | **5** | The annotated workbench (`a-vscode-docs-userinterface-img1.png`) shows an Explorer tree of ~20 rows, two editor groups with tabs and breadcrumbs, a minimap, a four-tab bottom panel, and a ~10-item status bar simultaneously — roughly 40 discrete information elements in one 1280-wide screen. Density is user-tunable via movable views (`a-vscode-docs-custom-layout-img3.png`) and a second side bar (`a-vscode-docs-custom-layout-img1.png`). |
| Navigation model | **5** | Layered model: activity-bar views, editor tabs + split groups (`a-vscode-docs-userinterface-img3.png`), per-editor breadcrumbs, Command Palette with `>` prefix, recently-used grouping and per-command gear (`a-vscode-ux-overview-img2.png`), Quick Pick with rich rows (`a-vscode-ux-overview-img3.png`), and a fully editable keybinding layer (`a-vscode-docs-keybindings-img0.png`). Even the palette's location is customizable (`a-vscode-docs-custom-layout-img4.png`). |
| Queue/status UX | **4** | Concurrent work surfaces as progress notifications with detail links (`a-vscode-ux-notifications-img5.png`) and status-bar progress items (`a-vscode-ux-statusbar-img2.png`); long-running output lives in tabbed panels (`a-vscode-docs-userinterface-img1.png`). The newer agent Sessions list in the right panel (`a-vscode-github-repo-img0.png`) shows per-session recency. Not a first-class work *queue* — no ordered pending/active/completed lane visible in captures — hence 4 not 5. |
| Presence and notifications | **4** | Severity-tiered notifications (info/warning/error: `a-vscode-ux-notifications-img2/3/4.png`), notifications that carry inline actions (`a-vscode-ux-overview-img4.png`), progress affordance, bell + badges in status bar and activity bar (`a-vscode-ux-statusbar-img0.png`, `a-vscode-docs-custom-layout-img1.png`). No multi-actor presence concept — it is a single-user tool — so "presence" maps to process/agent liveness only. |
| Status honesty | **3** | Honest about operational state and provenance: conflict notification demands user resolution (`a-vscode-ux-overview-img4.png`), settings carry "Modified elsewhere" provenance and modification bars (`a-vscode-docs-settings-img2.png`, `a-vscode-docs-settings-img3.png`), keybindings expose a Source column (`a-vscode-docs-keybindings-img0.png`), Settings header shows "Last synced" age (`a-vscode-docs-settings-img0.png`). But there is no verified-vs-self-reported-vs-unknown epistemic tier for agent/provider state — sync status is trusted at face value. |
| Empty/loading/error states | **4** | Errors are actionable notifications with recovery buttons (`a-vscode-ux-overview-img4.png`); loading is explicit progress (`a-vscode-ux-notifications-img5.png`, `a-vscode-ux-statusbar-img2.png`); the zero-editor state is a Welcome tab (`a-vscode-docs-accessibility-img2.png`). Empty states are utilitarian rather than instructional — no checklist/onboarding affordance visible in captured artifacts. |
| Accessibility | **5** | Dedicated doc page (`a-vscode-docs-accessibility.png`); automatic screen-reader detection with an explicit opt-in dialog (`a-vscode-docs-accessibility-img1.png`); high-contrast theme across the whole workbench (`a-vscode-docs-accessibility-img2.png`); a first-class, editable keyboard layer (`a-vscode-docs-keybindings-img0.png`); tab-focus mode toggle documented in the dialog text. |

## 5. Proposed revision packet seeds (ranked by expected impact)

1. **Promote "Go to…" into a real command palette.** Problem: the palette only routes to pages — flat list, no fuzzy match, no recents, no commands, no key hints (`populated/populated-command-palette.png`, `empty/empty-command-palette.png`). Evidence: `swipe/worker-2/a-vscode-ux-overview-img2.png` (recents + commands + per-item gear), `a-vscode-ux-overview-img3.png` (rich two-line pick rows), `a-vscode-docs-custom-layout-img4.png`. Rough scope: renderer command-palette component + a small command registry (pages, New request, Add agent, per-project "Open project", NEEDS YOU actions); must keep the palette read-only w.r.t. authority — commands dispatch through existing store/actions.
2. **Make the status bar an actionable surface.** Problem: `0 working · 1 need you · 8 agents` (`live/f-11-attention-panel.png`, `live/live-20-settled-office.png`) is static text; users must infer where to click. Evidence: `swipe/worker-2/a-vscode-ux-statusbar-img0.png` (every segment is an item), `-img2.png` (progress), `-img3.png`/`-img4.png` (error/warning severity coloring). Rough scope: status bar component — segment-level click targets (agents → Agents filtered by status; "need you" → open NEEDS YOU; "failed lately" → History filtered), hover detail, severity tint on the failure segment.
3. **Two-line record rows for request/project lists.** Problem: list rows are single-line and sparse (`populated/populated-projects.png`, request rows in `live/f-20-project-detail.png`); the deleted second line is where recency, status reason and attribution live. Evidence: `swipe/worker-2/a-vscode-ux-overview-img3.png` (icon + title + metadata + description per row at ~half the office row height). Rough scope: request-row and project-row renderer components + list styles; carry existing fields (status reason, provider state, timestamp) into a sub-line — no schema change.
4. **Settings search + modified indicators + scope discipline.** Problem: `populated/populated-settings.png` shows a long tabbed page with no search, no "changed from default" marker, and no visible split between office-managed and user-edited state. Evidence: `swipe/worker-2/a-vscode-docs-settings-img2.png` (query → "5 Settings Found", per-group counts, "Modified elsewhere"), `a-vscode-docs-settings-img3.png` (blue modified bars). Rough scope: Settings page — filter input over existing sections, per-row "modified" marker, keep the existing honest provenance text untouched.
5. **Inline actions on failure/attention items.** Problem: NEEDS YOU item and expanded request row (`live/f-11-attention-panel.png`) say *what* failed but push the fix behind "Open the request". Evidence: `swipe/worker-2/a-vscode-ux-overview-img4.png` (notification carrying Accept Remote / Accept Local / Show Conflicts). Rough scope: attention panel + request row — add bounded inline actions (Open, Retry, Cancel) that call existing request actions only; no new authority.
6. **Breadcrumb/context line on detail surfaces.** Problem: project detail and request rows (`live/f-20-project-detail.png`, `live/f-21-request-open.png`) don't show the path back (Project ▸ Requests ▸ request). Evidence: `swipe/worker-2/a-vscode-docs-userinterface-img3.png` (per-editor breadcrumbs). Rough scope: detail-page headers — small breadcrumb trail composed from existing route state.

Constraint carried into every seed: preserve the office's status-honesty language (verified / provider-reported / unknown) — it is the one dimension where the office already beats the comparator.

## 6. Gaps and honesty notes

- **Evidence is doc-curated, not live.** All VS Code product-UI images are Microsoft-published doc/guideline screenshots captured verbatim (`a-*-img*.png`) — they show intended UI, not a session I drove. The one independent live capture is `swipe/worker-2/a-vscode-github-repo-img0.png` (README "VS Code in action"), which corroborates the doc anatomy. Claims about *interaction* (fuzzy match behavior, keyboard flow) rest on the docs' own depictions and labeled alt text (`capture-manifest.json`); runtime behavior beyond that is inference and is labeled as such where used.
- **No method-b/c/d artifacts** — method (a) covered every target on the first pass; no coverage gap to report.
- **Baseline-side inference flagged in-table** — e.g., "the office palette is keyboard-reachable" and "office contrast may be marginal" are inferences from static PNGs; worker-7's self-audit should confirm or kill them.
- **Scoring skew warning**: VS Code is a decade-mature product whose docs I could not *fail* to find; the office is a pre-1.0 internal tool. Scores are absolute, not effort-adjusted; section 4 comparisons are the decision-relevant output.
- Third-party screenshots live only under `swipe/worker-2/` (outside Git); nothing in this commit contains captured third-party content.
