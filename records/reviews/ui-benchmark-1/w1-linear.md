# UI benchmark — worker-1: Linear comparator study

Round: `ui-benchmark-1`. Comparator: **Linear** (linear.app marketing site, public docs, changelog, blog). Focus: queue/status UX, agent UI, information density, navigation model. Office baseline: `drafts/organizer/ui-baseline/` (packaged App build mirroring main `65bddec`). Findings only — no product code changed.

## 1. Scope and capture method used per artifact

Capture preference order per the round request: **(a)** direct free capture via Playwright from `app/node_modules/playwright`, **(b)** free MCP/partial reports, **(c)** free pattern galleries, **(d)** document the gap.

All captures used method **(a)**: headless Chromium via the repo's bundled Playwright 1.63.0, launching the system-installed Google Chrome (`channel: 'chrome'`) at a 1600×1000 viewport, `domcontentloaded` + up to 15 s `networkidle` + 3.5 s settle, then a full-page screenshot plus a saved `.html` DOM snapshot. Two scripted passes ran on 2026-09-30; logs are `swipe/worker-1/capture-log.json` and `swipe/worker-1/capture-log-2.json`. Methods (b) and (c) were not needed — direct capture covered every target; nothing was purchased or gated behind payment.

Coverage caveat: no Linear account exists, so the live app UI could not be captured directly. `linear-02-product` proofed this — it rendered Linear's login wall instead of the app. Real-app evidence therefore comes from Linear's own screenshots embedded in docs pages and marketing pages (method a capture of their published material). That is still direct evidence of shipped UI, but it is Linear-selected evidence, which is a bias noted in section 6.

## 3. Comparator scorecard — Linear

Seven rubric dimensions, scored 1–5 with artifact citations.

| Dimension | Score | Evidence |
| --- | --- | --- |
| Information density | **5** | The real-app screenshot in `swipe/worker-1/linear-18-docs-my-issues.png` shows ~28–32 px grouped rows (ID + priority icon + title + status glyph), group headers with counts ("In Review 1", "In Progress 1", "Backlog 1"), four tabs, and a slim sidebar — roughly 15+ rows per viewport vs the office's card-per-row lists. `linear-21-docs-display-options.html` documents a per-view "Display properties" picker (choose which fields appear), grouping/sub-grouping, and layout toggle — density is user-tunable, not fixed. |
| Navigation model | **5** | Doc nav + app screenshot (`linear-18`) show a layered model: sidebar (Inbox, My issues, Pulse, Reviews, Favorites, then team-scoped Issues/Projects/Initiatives/Cycles/Views), `G then <letter>` goto routes (`G I` inbox, `G M` my-issues per `linear-17/18` HTML), `⌘K` fuzzy command menu (improved to fuzzy search per `linear-26` changelog), favorited views pinned to sidebar (`linear-19`), and URLs that carry filter state for sharing (`linear-19` "Copy view URL"). Multiple parallel routes to the same object (sidebar, goto, ⌘K, favorites, URL). |
| Queue/status UX | **5** | `linear-18` HTML: assigned issues auto-grouped in "focus order" — urgent, SLA-bound, blockers, cycle work, other active, triage, backlog, completed — sections appear only when non-empty, ordered by priority with started first. `linear-21`: ordering by status shows "closest to done → farthest from done" to surface active work. `linear-05`: Triage is a first-class intake queue with keyboard verbs (accept `T`, decline, duplicate, snooze). `linear-23`: fixed status categories with per-team custom statuses and system-managed Duplicate. `linear-22`: cycles automate queue hygiene (rollover, auto-add). ## 5. Proposed revision packet seeds — ranked by expected impact

Proposals only — no roadmap edits, no product changes. Rough file scope names renderer modules as orientation for the organizer, not a committed file list.

1. **Focus-ordered work queue.** Problem: `live/f-10-office-failed.png` shows the request list purely date-ordered — a stale Canceled row and three Drafts sit beside/above the live "A Step Failed" item needing action; nothing groups by attention class. Linear evidence: `swipe/worker-1/linear-18-docs-my-issues.png` + `.html` (curated focus order: urgent → blockers → active → triage → backlog → done, sections hidden when empty). Proposal: group office request rows by attention class (failed-needing-you → needs-you → running → drafts → closed), priority-ordered within group, collapsible headers with counts. Rough scope: `app/src/renderer/queue.tsx`, ordering helper + unit tests.
2. **Attention center: priority split + snooze.** Problem: `live/f-11-attention-panel.png` NEEDS YOU is a single undifferentiated dropdown — no read/unread, no snooze, no reminder, one badge channel; `live/live-20-settled-office.png` status bar compresses "1 working · 0 need you" into one line. Linear evidence: `swipe/worker-1/linear-17-docs-inbox.html` (Priority tab, snooze/reminders, badge-count config), `swipe/worker-1/linear-26-changelog-priority-inbox.html` ("something like a review blocking a release never gets buried"). Proposal: two-tier NEEDS YOU (action-required vs FYI), per-item snooze-to-time, reminders on requests, keep the existing honest "N need you" counter. Rough scope: `shell-widgets.tsx` attention panel + notification store schema (organizer-owned, must go through Session 8 for schema/IPC).
3. **Honest-but-clear agent state labeling.** Problem: `live/live-11-running-agents.png` shows a dispatched agent as "Unknown" while the status bar says "0 working · 1 need you" — technically honest, practically reads as broken; the office scene (`live-20`) later says "1 working", so two surfaces disagree mid-run. Linear evidence: `swipe/worker-1/linear-16-docs-coding-sessions.html` ("you'll be notified when your input is needed" — attention on state *transitions*, not a permanent unknown badge), `linear-14` (delegation stays attributed to a human owner). Proposal: keep the UNKNOWN tier but render it as "Contacting provider…" / "Awaiting first receipt" with elapsed time, and count it as working-pending rather than need-you. Rough scope: `agents.tsx`, `office-scene.tsx`, `shell-widgets.tsx` status line; label map in shared status helpers (cross-scope, organizer review).
4. **Per-view display options (group/order/fields).** Problem: `live/live-10-running-office.png` agents table and `live/f-10-office-failed.png` request rows are fixed-layout — no grouping, ordering, or density control; `populated/populated-projects.png` wastes a page on one card. Linear evidence: `swipe/worker-1/linear-21-docs-display-options.html` (`Shift V` display options, grouping + sub-grouping + sticky headers, display-property picker, personal vs workspace defaults). Proposal: minimal display-options menu on Agents/Projects/Requests views: group-by, sort, compact-density toggle, persisted per user. Rough scope: `queue.tsx`, `agents.tsx`, `projects.tsx`, small view-preference store.
5. **Keyboard-first command palette.** Problem: `populated/populated-command-palette.png` is a flat list with no key hints, no fuzzy match evidence, no grouping — mouse-shaped. Linear evidence: every captured doc (`linear-17/18/21` HTML) documents `Keyboard | Mouse | Command menu` triplets with keyboard first; `linear-26` changelog: fuzzy command-menu search. Proposal: visible shortcut hints on palette rows and nav items, `G+<letter>` page routing, fuzzy matching, recent/command groups. Rough scope: command palette component in `main.tsx`/components, keymap module, e2e keyboard test.
6. **Delegated-work visibility for agents.** Problem: `live/live-20-settled-office.png` shows a working bubble + "provider-reported activity" line, but there is no per-agent activity surface — what step, what evidence, what needs me. Linear evidence: `swipe/worker-1/linear-14-docs-agents-in-linear.html` (agent user pages, Delegate-filtered views/Insights), `linear-16` (session row on the issue, verification screenshots/recordings reviewable next to diffs). Proposal: an agent activity drawer per seat — current hop, elapsed, last verified receipt, attached verification artifacts, "notify me when input needed" toggle. Rough scope: `agent-drawer.tsx`, `activity.tsx`, request/job record links.

## 6. Gaps and honesty notes

- **No live-app capture.** `swipe/worker-1/linear-02-product.png` proves the app itself sits behind login; every real-app claim cites Linear's own published screenshots (docs/marketing) — a curated, vendor-selected sample that likely flatters density and polish. Where evidence is vendor-published, the claim cites the artifact, not independent observation.
- **Headless rendering gaps.** Media-heavy sections of `linear-01`, `linear-27`, `linear-28` contain dark un-rendered regions (lazy video/canvas not captured in stills); textual claims from those pages rely on the `.html` companions, not the partial pixels.
- **Accessibility is partially inferential.** Keyboard model and aria-label evidence is direct (doc tables + saved HTML attributes); in-app contrast, focus order, and screen-reader output are *not* verified — flagged as inference wherever used.
- **Empty/error score is evidence-limited.** Only Linear's docs-404 and login wall were capturable; a 3 does not mean their in-app empty states are poor — the public corpus simply doesn't show them. The office's empty states, by contrast, are fully evidenced in `empty/`.
- **404 artifacts retained deliberately.** `linear-03/04/06/08/09/13` are wrong-slug guesses that produced real 404 renders; they are listed as error-state evidence, not failed captures. All five `.html` companions are saved.
- **Locale note on baseline.** Baseline shots show Korean-locale dates ("9월 30일 오전 4:35") and mixed copy ("1 active projects", "1 participants", "A Step Failed") — flagged so the grammar findings in §4 are not misread as translation artifacts.
- **No purchase, no account, no MCP gallery.** Method (a) covered the full target set; methods (b)/(c) unused; nothing was purchased or bypassed.
