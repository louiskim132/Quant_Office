# Implementation increments and acceptance — architecture 0.3

The completed design specifies a general quant research team, a graphical Windows EXE, provider-hosted agent work and a strictly external user-operated Colab boundary. This is the executable build sequence. No increment is marked operationally complete by architecture documents alone.

## Increment 1: domain contracts and isolated team contexts

Implement versioned schemas, canonical identities, role definitions, project/experiment/task scope, scientific-policy applicability, evidence origins and approval dependencies. Build mock event fixtures before any autonomous provider delegation.

Acceptance:
- Two different research descriptors, such as a forecast and risk estimator, validate without CatBoost-specific defaults.
- Canonical hashes match cross-runtime golden vectors; required nulls, duplicate keys, unsupported versions and ambiguous units fail.
- Task/role identities cannot be forged by prose. Workers cannot approve output or change protected scientific/test definitions.
- Required missing evidence blocks; a predeclared inapplicable trading-cost policy does not block an unrelated claim.
- User imports and provider jobs have distinct origins and cannot be relabeled.

## Increment 2: Windows desktop shell and controller

Implement Electron/React office panels and a PixiJS office scene, typed preload IPC, SQLite event store/projections/outbox, artifact quarantine, budgets, task capacity and recovery. Supply an installer/EXE from a verified hosted build environment. Use clearly labeled mock providers initially.

Acceptance:
- A clean Windows user can launch the graphical app, create a project, issue a prompt, inspect mock task/review evidence, export code and import results without a terminal.
- Renderer commands are allowlisted; hostile report markup and archive paths cannot execute or escape.
- Office animation and task board agree with recorded state, including idle, blocked and unknown/offline status.
- Restart preserves reports, approvals, queued imports and unknown submissions without duplicate jobs.
- Two worker slots are enforced globally across projects, including nested tasks.
- No local agent execution or Colab command/adapter exists.

## Increment 3: hosted agents and real independent verification

Resolve the requested model targets and probe inference, hosted execution, files, dependencies, network restrictions, cancellation and metering. Enable paid dispatch only within configured user limits. Run one bounded implementation task and separate verification task on allowed provider infrastructure.

Acceptance:
- Raw provider receipts prove executable tools ran on OpenAI/Anthropic infrastructure.
- Worker output routes through the supervising PM; A/B first reports persist before cross-disclosure.
- There is one rebuttal per participant; Director decisions bind exact verified bundles.
- A provider lacking a required package/capability blocks or routes to an approved provider profile, never local/Colab.
- Unknown submission reconciles before retry, usage is not reset, and cancellation is not reported until acknowledged.
- Concurrent jobs reserve maximum enforceable liability against every shared ceiling; low estimates cannot overcommit it, and unknown charge bounds block dispatch.
- The hosted network/tool configuration cannot reach/control Colab or remote notebook sessions.

## Increment 4: finalized code export and explicit result import

Implement a reproducible reviewed archive containing source, configuration, dependencies, tests, static launcher/instructions, expected outputs and manifest. A handoff records export to the user only. The user independently runs finalized code in Colab; returned files enter only through explicit user import.

Acceptance:
- No browser opener, login, live Drive notebook access, API, callback, polling or remote-control path connects the team to Colab.
- The user's static launcher contains no agent API calls or team callback/control listener.
- No model calls occur for the waiting experiment until the user supplies results or a new instruction.
- Changed package/notebook/data identities invalidate affected approval; partial outputs remain incomplete.
- Payload inventory, detached approval envelope and outer transfer receipt have no circular hash dependency; changed outer packaging cannot silently change the approved payload.
- Hosted verification of imported copies checks schemas, row/key counts, actual schedule and required scientific gates.
- An accepted preflight import leaves the waiting state before hosted validation; full-run approval remains blocked until validation and its explicit smoke prerequisite are satisfied.
- External run provenance remains user-attested unless and until a separately recorded provider reconstruction supports a stronger claim.

## Increment 5: complete one real generalized research cycle

Select a mandate and freeze its dataset, output meaning, model/baselines, metrics, scientific/economic policies, exposures and budget. Complete provider-hosted development/verification, user-mediated preflight/smoke/full-run exports, explicit imports and independent C/D analysis.

Acceptance:
- Required structural failures stop expensive computation and emit failure artifacts.
- C and D receive the same evidence independently and reconstruct required calculations on provider infrastructure.
- Invalid, inconclusive, valid negative, engineering completion and advancement remain distinct.
- The Director receives original positions, rebuttals, objections and evidence and records a reopening condition.
- A changed scientific decision creates a new contract and invalidates dependents.
- One project's data and approvals cannot leak into another by filename, context reuse or cache identity.

## Increment 6: evaluate team quality and broaden projects

Compare role assignments using seeded defects, valid controls, evidence quality, false positives, cost and elapsed time. Add other quant projects through the research-package interface. Improve cache specificity, archive handling and desktop polish after correctness.

Acceptance: a second model family runs through the same team/controller without hardcoded controller scientific logic. Expand worker capacity or models only by user-approved configuration supported by observed results. Later strategy redesigns are separately registered experiments, not relabeling of prior predictions.

## Required verification matrix

| Area | Mutations / interruption | Valid control |
| --- | --- | --- |
| Execution boundary | Agent requests local shell, local module import, browser/Colab tool, remote Jupyter endpoint or live notebook fetch | Hosted tool execution with verified provider receipt |
| Units and costs | Factor-of-ten spread, missing exit fee, conflicting prose/units | Independent arithmetic oracle and consistent structured report |
| Data presence | Absent required column versus all-NaN column | Required measured evidence present and aligned |
| Chronology | Late warm-up, forward horizon crossing, next-bar feature, stacked-row purge | Causal features and shared wall-clock boundaries |
| Data geometry | Duplicate/resampling loss, short/long gap reset defects | Exact row reconciliation and intended reset behavior |
| Statistical policy | Unsupported family count or invented threshold | Explicitly supported family/power policy or named blocker |
| Hard gates | Audit failure followed by expensive fit, empty invalid data reported as null | Stop/failure bundle; valid negative result preserved |
| Identity/resume | Changed fees/source/data/dates/features/labels/folds/tests/environment/launcher, partial output write | Unchanged complete inventory resumes |
| Review isolation | A conclusion leaked to B; C/D shared first context; worker self-certification | Independent committed reports and bounded rebuttals |
| Recovery/spend | Lost submission response, app close, sandbox expiry, duplicate import | Idempotent reconciliation and preserved budget reservation |
| Project scope | Cross-project report/approval/artifact substitution | Explicit authorized evidence import with lineage |
| Protected data | Mixed/unclassified partition or protected-derived report sent under general project grant | Classified permitted partition; any protected access has user authority and exposure recorded before transfer |
| Smoke gate | Full-run request without smoke evidence or an enforced in-package smoke gate | Accepted compatible smoke or reviewed fail-closed launcher ordering |
| User results | Missing terminal manifest, forged provider origin, live Colab URL | Explicit file import with honest external provenance |

Project-specific mutations are selected by the frozen contract. The CatBoost example supplies some historical fixtures; it does not impose them on every study. Test definitions are reviewed independently from patches that could weaken them.

## Evidence required per increment

Export source and test-definition hashes, exact environment/capability identity, patch/archive, executor receipts, raw logs, structured results, fixtures, known limitations and actual usage. Record PM-A's implementation position and PM-B's independent verification position separately. Never present a self-check as independent certification.

Current evidence covers documentation consistency, draft JSON parsing and reference-file byte identities only. No executable platform, real adapter probe, research test or Windows release has been produced yet. Approved hosted execution/build access, budgets and storage configuration are implementation setup requirements; no new scientific facts are needed to finish the architecture.
